# Geodetic, concurrency, and resource audit — 2026-10-09

Audited commit: `cc0e20c` (`Reject compacting streamers in the PMTiles tiler`). Production code was not changed. Findings distinguish executable reproductions from code inspection and proposed improvements.

**Assessment:** the core direct raster-sample-to-H3 engine has substantial correctness coverage, but the repository is not generally geodetically valid for all advertised inputs. CRS interpretation and mosaic selection can produce large positional errors or discard valid observations. Address these before adding more speculative indexing shortcuts.

## Validation performed

- `cargo test --lib --tests --offline`: 385 reported passed, 0 failed, 6 explicitly ignored across 37 test binaries. This includes unit tests and geodetic, exact-assignment, rotated-grid, horizon, antimeridian, spill, prefetch-failure, sharding, and threading integration tests.
- The initial sandboxed run silently returned early from localhost-dependent tests. A separate networking-enabled remote-reader run was started; its result is recorded below.
- Independent local PROJ 9.8.1 `cs2cs` comparisons for custom units and prime meridians.
- Standalone Rust probes linked against the freshly compiled library: CRS variants, custom GeoTIFF scale metadata, SQL-equivalent mosaic opening, rotated mosaic ownership, and instrumented kernel thread IDs.
- No production DuckDB SQL session, race sanitizer, release throughput benchmark, or peak-RSS benchmark was run. Passing existing tests is not a proof that every projection or concurrency schedule is correct. No percentage speedup is claimed.

## Reproduced correctness defects

### P1 — CRS fast paths ignore meaningful parameters

`src/crs/transformer.rs:180` and `:450`: dispatch examines only a subset of PROJ parameters. Albers accepts `+units=us-ft` but executes metre formulas. Geographic identity accepts `+pm=paris` without shifting longitude. Other modifiers, including axis/ellipsoid overrides, need a complete audit of fast-path eligibility.

For `+proj=aea +lat_1=29.5 +lat_2=45.5 +lat_0=23 +lon_0=-96 +datum=NAD83 +units=us-ft`, input `(1580000, 1940000)` gives:

| Implementation | Longitude | Latitude |
| --- | ---: | ---: |
| Repository | -77.4444087567 | 39.0923210269 |
| PROJ, inverse to NAD83 geographic | -91.1030319046 | 28.2800931283 |

The repository returns the same result for metre and US-survey-foot definitions. For `+proj=longlat +datum=WGS84 +pm=paris`, input `(2,45)` returns `(2,45)` instead of PROJ's `(4.3372291667,45)`.

**Fix:** validate the complete definition before selecting a fast path; normalize supported units/axes/prime meridians or use a transformation backend that honors them. Reject unsupported modifiers rather than silently dropping them. PROJ documents these parameter semantics in its [projection reference](https://proj.org/en/stable/usage/projections.html).

### P1 — Geographic fallback passes degrees where proj4rs expects radians

`src/crs/transformer.rs:566`: the generic transformation passes raw `(x,y,0)` into proj4rs and only converts the output from radians. This fails when a geographic source falls outside the identity fast path.

Probe: `+proj=longlat +ellps=clrk66`, input `(2,45)`, returns `(114.5915590262,2578.3100780887)`. The walker subsequently excludes out-of-range latitude, so valid pixels can disappear instead of producing an error (`src/aggregator/multi_horizon/walker.rs:234`).

**Fix:** convert geographic input angles to radians before calling proj4rs; explicitly validate output domain and define whether transformation failures abort or are counted/skipped. Datum handling is a separate requirement.

### P1 — Custom GeoTIFF projection decoding uses the wrong scale key

`src/raster/metadata.rs:200` reads Transverse Mercator scale from key 3076. That is the linear-units key; natural-origin scale belongs to key 3092. A synthetic user-defined TM GeoTIFF with key 3092 set to `0.9` was parsed as `+k=0.9996`.

The custom GeoKey and WKT reconstruction paths also hard-code `+units=m`, and unrecognized datums can default to WGS84. This is unsafe for feet-based custom projections and unsupported datum definitions.

**Fix:** use the correct keys, preserve linear/angular units and datum/ellipsoid definitions, and fail on incomplete or unsupported definitions. Replace the substring-based WKT parser with a standards-aware backend or document and strictly enforce a narrow supported subset. See the [OGC GeoTIFF standard](https://docs.ogc.org/is/19-008r4/19-008r4.html).

### P1 — Antimeridian tile filtering rejects valid SQL inputs

`src/raster/mosaic.rs:412` applies ordinary interval comparisons to a possibly crossing longitude bbox. SQL goes through this path even for one input file (`src/functions/bind_utils/lifecycle.rs:116`). Existing antimeridian tests primarily use `from_single_reader`, bypassing this tile-level rejection.

Probe: a 10×10 raster spanning longitude 178–179 and latitude -17–-16, queried with bbox `[178,-20,-178,-15]`:

- Single-reader streamer: count **100**.
- `MosaicReader::open` on that same file: **“No mosaic tiles intersect the requested bounding box.”**

**Fix:** share wrap-aware interval intersection logic across tile, chunk, and sample filters. Add regressions through the actual SQL/mosaic initialization path. Bounds used to reject data must conservatively include the true footprint; sampled projected bounds alone are not a general certificate.

### P1 — Mosaic ownership confuses bounding rectangles with footprints

`src/raster/mosaic.rs:511`: `First` and `Cutline` select candidate owners using WGS84 bounding rectangles, without proving the point is inside the candidate raster. Rotated/projected rasters do not generally fill those rectangles.

Probe: a 100-pixel diamond-shaped rotated raster with corners `(0,1),(1,2),(2,1),(1,0)` plus a disjoint 100-pixel square in `[0.1,0.2]×[0.1,0.2]`. `First` returns **100**, while the correct union count and `Average` return **200**. All pixels in the square are falsely suppressed by the diamond's bbox.

**Fix:** use bbox/spatial indexes only for candidates, followed by a valid footprint or inverse-coordinate membership test. Specify nodata fallback semantics. The cutline distance currently uses squared longitude/latitude differences; offer an explicit suitable metric if geographic nearest-tile behavior is intended, including longitude wrapping.

## Validity boundaries that must be explicit

- Affine rotation/shear and PixelIsPoint half-pixel handling are implemented and tested. Direct H3 indexing occurs independently at each requested resolution. Conservatively disabling early eviction for uncertified generic projections is appropriate.
- EPSG:4269 uses identity, and the Albers fast paths do not perform datum shifts. Golden tests explicitly use the source ellipsoid/datum as their target. Their 0.01 m tolerance measures inverse-projection agreement, **not absolute WGS84 accuracy**. A small datum displacement can change assignments near cell boundaries at any resolution.
- EPSG:27700, 7856, and 6933 all reproduced “Unsupported EPSG” although the CRS documentation advertises them. `+init=epsg:...` is not a functioning general CRS database fallback in this configuration. The documentation also incorrectly places 5070 under Lambert and 6933 under Albers.
- Current counts/means are sample-weighted. Supersampling approximates pixel contributions; it is not exact area intersection or generally ground-area weighting. Claims of “strict hexagonal area weighting” and universal `<0.5%` center-sampling error in `docs/super-sampling.md` are not established by the implementation.
- H3 uses a spherical model. Keep its native indexing conventions; do not introduce an extra latitude conversion merely because its radius is authalic. See [H3's model](https://h3geo.org/docs/core-library/overview/).
- Hierarchical compaction is a logical aggregation operation, not a geometrically identical replacement for direct coarse indexing. [H3 documents approximate geometric containment](https://h3geo.org/docs/).
- WKB export unwraps ordinary dateline cells but intentionally leaves pole-cell rings unchanged (`src/encoding/wkb.rs:28`). These are not faithful polar-cap geometries for planar GIS operations. GeoParquet declares planar edges, so exported boundaries also approximate spherical H3 edges.

## Multithreading findings

### P2 — Caller context silently disables kernel parallelism

`src/aggregator/multi_horizon/controller.rs:512` runs ordinary iterators whenever `rayon::current_thread_index().is_some()`. Thus entering the streamer through `ThreadPool::install` makes its aggregation windows serial, regardless of pool size.

An instrumented wrapper around the real continuous kernel processed a 256×256 raster:

| Caller | Pool size | Distinct kernel thread IDs | Total weight |
| --- | ---: | ---: | ---: |
| Ordinary caller | 10 | 10 | 65,536 |
| `pool.install` | 1 | 1 | 65,536 |
| `pool.install` | 2 | 1 | 65,536 |
| `pool.install` | 4 | 1 | 65,536 |
| `pool.install` | 8 | 1 | 65,536 |

Distinct IDs are not simultaneous concurrency: the controller allows at most eight window jobs per wave, which can run on different members of the global pool over time. Decode workers are separate OS threads.

`tests/test_threading.rs` therefore does not establish scaling for its custom-pool cases. Its map collector also merges repeated output keys, which can hide duplicate emission in those particular tests. Other geodetic tests do check duplicates.

**Fix:** make execution ownership explicit, with an aggregation pool and an intentional reentrancy policy. Do not simply remove the serial guard: callers that hold a streamer mutex while other tasks on the same Rayon pool wait for it require deadlock regression tests. Instrument concurrent activity, not just pool size or elapsed time.

### P2 — SQL worker controls are unused

`workers` and `threads` are registered, and `parse_workers` exists (`src/functions/bind_utils/bind_helper.rs:282`), but no caller applies it. The configuration instead defaults to four decode workers; aggregation derives its task count from Rayon, capped at eight per wave. Remote fetching has another pool, defaulting to eight workers.

**Fix:** distinguish decode, aggregation, and network concurrency; apply a shared resource policy across concurrent queries. Test that the SQL options actually alter execution.

### What the design already does well

Worker-local maps avoid shared per-pixel locks. Worker waves join before serial merging and watermark advancement. Exclusive map ownership separates merge and eviction phases. The prefetch queue provides bounded ordered delivery, terminal errors, cancellation, and worker joins; the record queue provides demand-driven backpressure. Existing stress/failure tests passed. No data race was demonstrated, but no race detector or exhaustive schedule analysis was performed.

The 32 shards do **not** currently imply parallel merging: `controller.rs:535` merges worker maps serially. The old `examples/benchmark_scaling.rs` compares the streamer against a different per-chunk algorithm, so its timings cannot establish current streamer scaling.

## Performance and memory work worth implementing

These preserve semantics when implemented with the listed constraints. Benefits require release-mode measurement; the ordering is an engineering priority, not a measured speedup ranking.

| Priority | Change | Expected benefit and correctness condition |
| --- | --- | --- |
| 1 | Fix execution policy and wire SQL worker controls | Enable real custom-pool parallelism and prevent per-query oversubscription. Preserve failure, cancellation, and join-before-eviction behavior. |
| 1 | Budget decoded bytes, not just queued chunks | Bound queued, in-worker, and recycled buffers together. Sixteen 2048×2048 Float32 chunks alone are 256 MiB; the 64 MiB aggregation budget excludes them. Acquire reservations before decoding. Reject or explicitly handle a single chunk larger than the budget. |
| 1 | Account for compaction and all output state | `HierarchicalCompactor::pending` retains parent accumulators and child states outside active-map accounting. Flushes can append many children before the controller rechecks output limits. Add byte accounting, incremental emission, and a bounded/spillable grouping strategy. Current budget is not a hard RSS ceiling. |
| 2 | Reuse worker scratch and simplify memory checks | Worker maps and borrowed raster buffers are already reused. Also reuse per-window vectors/run accumulators. For inline-only continuous statistics, avoid scanning every cell to sum a guaranteed-zero heap cost; use specialized/incremental accounting. |
| 2 | Merge disjoint shards in parallel when profiling warrants | Partition owned results into shards and merge with exclusive shard access. Reserve memory globally and join all shard work before advancing the horizon; do not race spill or eviction. The serial merge stage is a candidate bottleneck, not a measured one here. |
| 2 | Cache the two pole H3 indexes per resolution | WKB currently performs up to two constant pole-to-cell conversions per emitted polygon. Precompute the 32 indexes; geometry semantics remain unchanged. Benchmark geometry-heavy exports. |
| 2 | Bound per-worker decoder caches for large mosaics | Each worker retains a decoder slot per tile and opens decoders lazily. Use an LRU/last-use strategy to bound open files and decoder state; preserve buffer ownership and avoid unnecessary reparsing. |
| 3 | Add certified bounds for specific additional projections | Generic PROJ paths retain/spill until EOF. Proven bounds for selected UTM/polar cases may reduce memory, spill I/O, and latency. Fixed padding or sparse boundary samples are insufficient proof. |

Avoid presenting already-implemented borrowed decoding, buffer reuse, no-data pruning, spill merging, or sample-weight coalescing as new optimizations. Do not derive direct coarse assignments by taking fine-cell parents, or skip H3 indexing across a span based only on matching endpoints. Those shortcuts can change boundary assignments.

## Features to add, in order

1. **Strict CRS mode and provenance:** supported-CRS inspection, full unit/axis handling, explicit datum approximation policy, selected transformation and accuracy metadata. Consider an optional full-PROJ backend for WKT2, database-backed EPSG resolution, datum grids, and epoch-aware transformations.
2. **Scientifically defined weighting:** separate sample mean, area-weighted mean, and extensive-total redistribution. Add coverage area/fraction and valid/nodata area. Offer conservative pixel–cell overlap or an adaptive approximation with stated error controls; distinguish spherical from ellipsoidal area.
3. **Reliable mosaics:** footprint-aware ownership, documented first-valid/nodata fallback, dateline-aware selection, and an explicit overlap model for differing pixel sizes. `Average` currently accumulates all observations, so finer grids and overlap density receive greater weight.
4. **Operational controls and diagnostics:** actual worker limits, decoded-byte budget, spill directory/quota, cancellation, transformation-failure counts, per-stage timings, queue bytes, spill bytes, and observed peak RSS. Export an execution summary with provenance.
5. **GIS-safe geometry:** dateline splitting into MultiPolygon, correct polar-cap construction, optional edge densification with a tolerance, and metadata matching the resulting geometry types.
6. **Raster value semantics:** band scale/offset, mask/alpha validity, and band-specific nodata. Apply scale/offset before spectral formulas where required; do not assume raw stored values are calibrated values.
7. **Independent verification harness:** native PROJ/GDAL control points, production SQL entrypoint tests, full accumulator comparisons across actual parallel execution, duplicate checks, random rotations/units/projections, and peak-RSS tests under small budgets and slow consumers.

## Acceptance criteria for follow-up work

First turn the executable defect cases above into regression tests and repair them. Then compare each optimization against a direct reference for cell IDs, counts, sums, min/max, variance, categorical histograms, quantiles, and duplicate output. Exact IDs/counts should remain exact where mathematically appropriate; floating-point merges need explicit tolerances or a deterministic mode.

For performance, run the **same production pipeline** in release mode at 1/2/4/8 aggregation workers, controlling decode/network concurrency independently. Include WGS84, Albers, generic projected data, coarse/fine H3, supersampling, high-cardinality categories/quantiles, multiple concurrent queries, and forced spill. Record throughput, first-row latency, peak RSS, worker activity, merge time, and spill bytes. Repeat warm/cold runs and report distributions. The current audit supports these optimization opportunities, not a promised speedup.
